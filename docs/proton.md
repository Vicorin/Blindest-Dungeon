# Wine / Proton version proxy

BlindestDungeon still installs as `version.dll` beside the **64-bit**
`Darkest.exe`. The injection worker, game hooks, offsets, input, and speech code
are unchanged by this patch.

The old proxy in `Source/Mod/src/core/hooks.cpp` used 17 MSVC linker pragmas
containing `\\.\GLOBALROOT\SystemRoot\System32\version.dll` PE forwarders.
Wine could not resolve those forwarders during FMOD initialization.

`src/core/version_proxy.def` now fixes the same 17 names and ordinals (1–17) to
local, typed `WINAPI` wrappers in `version_proxy.cpp`. Compile-time checks compare
all wrappers to the Windows SDK declarations. The uncommon
`GetFileVersionInfoByHandle` declaration follows
[Microsoft's documentation](https://learn.microsoft.com/en-us/windows/win32/menurc/getfileversioninfobyhandle).

On the first version API call, `InitOnceExecuteOnce` loads the absolute path
returned by `GetSystemDirectoryW`, using `LoadLibraryExW` with
`LOAD_LIBRARY_SEARCH_SYSTEM32`. It rejects a module equal to the proxy and rejects
any resolved export whose owning module is the proxy. It resolves **by name**,
since Wine's builtin ordinals differ from Windows. The backend stays loaded. Native Windows needs no DLL override or extra backend.
The incoming last-error value is restored before dispatch; the backend's result,
output buffers, and last-error value are passed through.

No DLL loading, logging, waiting, or proxy initialization was added to `DllMain`.
Like other lazy DLL proxies, the first API call must occur outside a caller's
`DllMain`; callers should not use version APIs to trigger loading under the
loader lock. The existing mod worker bootstrap remains in place.

## Build

On Windows, install the Visual Studio C++ x64 tools and Windows SDK, then run
from the repository root:

```powershell
powershell -File .\Source\Mod\build.ps1
```

The output is `Source\Mod\build\version.dll`. The existing script also attempts
to deploy to its configured Steam game directory, so close the game first.
Its export gate still checks names and ordinals against Windows System32, and
now rejects PE forwarders instead of requiring them. No extra runtime DLL or
third-party version implementation is needed.

The complete mod requires the MSVC ABI and the included `prism-static.lib`
(and the Visual Studio ATL support used by that library).
A Linux cross build can use clang-cl/lld-link with installed MSVC/Windows SDK
headers and libraries, the same source list and flags as `build.ps1`, and the
translation include generated by that script. MinGW's older `winver.h` prototypes
are not the reference signatures for building this module.

## Install and test in Proton

1. Back up the currently installed mod DLL. Copy the new x64 `version.dll` beside
   the x64 `Darkest.exe` (normally `_windows/win64`). Do not replace anything in
   the Proton prefix's System32 directory.
2. Use Steam launch options:

   ```sh
   WINEDLLOVERRIDES="version=n,b" PROTON_LOG=1 %command%
   ```

   `PROTON_LOG=1` is only needed while diagnosing. No additional override is
   required for the system backend.
3. Start the game. `version-proxy.log` beside the proxy should report the requested
   system path, a loaded backend at a distinct address, any missing exports, and
   initialization completion. Logging is independent of the mod's optional debug
   log. If the directory is unwritable, debugger output is still emitted through
   `OutputDebugStringW` (Wine's `+debugstr` debug channel can capture it).
4. Confirm the Proton log no longer reports GLOBALROOT forwarder failures, that
   FMOD initializes, and that the title/menu announcements work. Exercise keyboard
   navigation, speech, settings, and a raid. Repeat those checks on native Windows.

A rejected self-load or unresolved backend is logged and cached for the process
lifetime; the proxy never retries with an unqualified `LoadLibrary("version.dll")`.
An unavailable export sets `ERROR_PROC_NOT_FOUND` and returns failure: `FALSE`
for BOOL APIs, zero for size/language APIs, `VFF_BUFFTOOSMALL` for VerFindFile,
and `VIF_CANNOTREADSRC` for VerInstallFile. Those flag values are conservative
failure indications for APIs without a generic error return. Outputs remain
untouched when no backend function is available.

## Proton limitations and backend alternatives

Wine/Proton's builtin `version.dll` currently has no
`GetFileVersionInfoByHandle`; its missing-export diagnostic is expected. The proxy
retains that export and fails it explicitly rather than calling an unimplemented
Wine entry point. If a future game dependency requires it, matching native
Windows behavior would require an additional implementation. Native Windows
uses its real export without this limitation.

A KernelBase-only fallback was considered: Wine implements many version APIs
there, but it does not supply all 17, including VerInstallFile. API-set aliases
also do not guarantee a distinct version module. Neither is used as a partial
replacement. Copying/renaming a system DLL would add installation and dependency
risks. The validated system-module load avoids those changes. If a different
Wine build returns the proxy itself, this patch fails safely and logs that fact;
that build needs further loader/backend investigation.

## Focused checks

Check a built DLL's exact x64 export ABI with Python 3 (no packages needed):

```sh
python3 Source/Mod/tests/check_version_exports.py /path/to/version.dll
objdump -p /path/to/version.dll
```

The Python check requires exactly the original 17 names and ordinals, local code
exports, and no GLOBALROOT string. `dumpbin /exports` is the Windows alternative.

Build the API smoke test in an x64 Visual Studio tools shell:

```bat
cl /nologo /std:c++17 /EHsc /MT Source\Mod\tests\version_proxy_smoke.cpp /Fe:version_proxy_smoke.exe
```

Put the executable beside the built proxy and run it **from that directory**.
Its name deliberately avoids the `Darkest.exe` bootstrap. It checks concurrent
first use, all name/ordinal lookups, A/W resource reads and queries, last-error
propagation, and the eight-argument APIs against the real system implementation.
It tests the missing ByHandle failure or compares its native implementation when
available. The smoke test can also be built with
`x86_64-w64-mingw32-g++ -std=c++17 -static` and run under Wine with
`WINEDLLOVERRIDES="version=n,b"`.

Passing these checks verifies proxy loading and dispatch, **not** the full game,
FMOD, or accessibility behavior. Record the exact runtime/build and game results
when submitting test feedback.

To test the recursion guard without relying on a particular Wine loader, build a
standalone fault-injection DLL in a separate directory in an x64 tools shell:

```bat
cl /nologo /c /std:c++17 /EHsc /MT /DLoadLibraryExW=BdTestLoadLibraryExW Source\Mod\src\core\version_proxy.cpp /Fo:proxy.obj
cl /nologo /c /MT Source\Mod\tests\version_proxy_self_backend.cpp /Fo:fake.obj
link /DLL proxy.obj fake.obj /OUT:version.dll /DEF:Source\Mod\src\core\version_proxy.def kernel32.lib
```

Run the smoke executable there with `--expect-unavailable`. Both calls must fail
with error 127 and the log must report rejection of the proxy itself. This DLL
is a test fixture; use the normal build for the game.

## Validation recorded for this patch

The released v1.1.1 DLL failed the new export check because its first export was
a PE forwarder. The new standalone proxy built with clang-cl/lld-link and the
Microsoft Windows SDK passed the x64/name/ordinal/code-export check. Its API
smoke test passed with zero failures on Wine 11.19 and the Wine binary shipped
in Proton Experimental `experimental-11.0-20261027b-x86_64`, using isolated test
prefixes and `version=n,b`. The forced self-backend test also passed. These are
standalone proxy tests, run without Steam or the game.

A full mod cross-build compiled the sources but could not link against the local
MSVC 14.41 installation: Prism needs ATL's `_AtlBaseModule` and newer C++ runtime
symbols (`_Cnd_timedwait_for_unchecked`, `__std_find_last_of_trivial_pos_1`). Build
the complete mod with a sufficiently recent Visual Studio toolchain and ATL.
The standalone test DLL contains no accessibility mod and must not be installed
as the mod. Full-game/FMOD behavior, native Windows runtime behavior, and the
existing accessibility features have **not** been runtime-tested for this patch.
